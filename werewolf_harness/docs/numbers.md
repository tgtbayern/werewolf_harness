# 数字卡

每个数字都写清：值、口径、样本量、怎么复现。
环境：云上开发容器，**2 核**，Python 3.10，Postgres 16 和 Redis 7 都在本机。压测机器人、API、worker、数据库挤在同样这 2 核上。

**「模拟」的含义**：`sim*` 是模拟供应商（`app/llm/sim.py`），带对数正态分布的延迟、故障注入和按厂商公开规则实现的前缀缓存。凡是标「模拟」的数字，都没有花真钱、没有调真模型。它们能说明设计之间的相对差异，不代表真实账单或真实延迟。

## 压测：单进程能撑多少

场景：每张桌 1 个机器人真人（WebSocket 心跳、每收到一个事件就 GET 一次状态、轮到自己就出手），加 7 个 `sim-cheap` 模型座位（中位延迟 300 ms）。每档压 60 s，10 s 内逐步开桌。每档都重启服务、清空库。

**先 profile 再优化**：第一轮压到 100 桌时 API 进程 CPU 打到 91%。用 yappi（覆盖全部线程）profile 之后，CPU 大头是 FastAPI 的 `jsonable_encoder`：返回 dict 时它会先把整个对象树遍历一遍，比 `json.dumps` 慢约 11 倍（单个座位状态 1.35 ms 对 0.12 ms）。第二是熔断器每次记录都要对整个滑动窗口求和，是 O(n)。改成直接 `json.dumps`（`FastJSON`）、窗口计数改成增量维护、gateway 的 Redis 往返合并成 pipeline 之后，结果如下（LocalExecutor）：

| 桌数 | 改前 commits/60s | 改后 commits/60s | 改后事件推送 p95 | 改后出手确认 p95 | 改后 API CPU |
|---|---|---|---|---|---|
| 50 | 2182 | 2195 | 17 ms（改前 46） | 44 ms（改前 155） | 46%（改前 71%） |
| 100 | 2935 | **3947（+34%）** | 100 ms（改前 141） | 684 ms（改前 1193） | 88%（改前 92%） |
| 150 | 3221 | 3927 | 151 ms | 1526 ms | 90% |
| 200 | — | 3774 | 278 ms | 4674 ms | 89% |

同样的压测改用 `AGENT_EXECUTOR=streams`，也就是 1 个 API 进程加 1 个 worker 进程，二者都在这 2 核上：

| 桌数 | commits/60s | 事件推送 p95 | 出手确认 p95 | API CPU | worker CPU |
|---|---|---|---|---|---|
| 50 | 2189 | 22 ms | 51 ms | 26% | 48% |
| 100 | 3687 | 95 ms | **163 ms**（local 为 684） | **40%**（local 为 88%） | 77% |
| 200 | 3790 | 409 ms | 724 ms | 45% | 72% |

总吞吐和单进程差不多，因为 2 核已经用满。但 API 进程的 CPU 从约 90% 降到约 40%，所以真人出手的确认延迟 p95 从 684 ms 降到 163 ms：模型回合的 CPU 不再和连接处理抢同一个 GIL。要提高吞吐，就给 worker 加机器；API 进程不需要跟着扩。

**结论**：在 2 核机器上，单个 API 进程约 **65 步/秒** 时饱和，对应 **约 100 张**这种配置的桌。瓶颈是 CPU：Python 的 GIL 加上模型座位构造 prompt 和防护检查的 CPU 开销，而不是 IO。再往上要做两件事：
1. 把模型回合挪到 worker 进程（`AGENT_EXECUTOR=streams`，结果见下）；
2. 加核或者加机器横向扩容。

压测过程中还发现了两个隐藏的并发上限，都已修复并写成配置：
- `players/recovery.py` 里所有模型调用共用一个 32 线程的池，32 个并发调用就是整个进程的上限（`MODEL_CALL_THREADS`）；
- worker 用 `asyncio.to_thread` 跑回合，默认线程池只有 min(32, cpu+4) = 6 个线程，把 worker 卡在约 8 步/秒（改为独立线程池）。

原始结果：`loadtest/results/`。复现：`make run` 之后执行 `python -m werewolf_harness.loadtest.bots --tables 100`。
