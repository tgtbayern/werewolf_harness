设计札记 · Werewolf Arena

一个多智能体对抗环境该由什么来保证正确

本文记录的是若干设计决定的依据，以及其中两项后来被推翻的论断。它不是使用说明。

§1问题的定位：认知分发，而非流程编排

做多智能体系统时，第一反应是找个编排框架：把流程画成图，节点是智能体，边是流转条件。这套做法在协作型任务里够用——大家目标一致，信息共享，谁先谁后主要是效率问题。

对抗型任务不一样。狼人杀里有一件事是协作型任务里不存在的：不同的参与者对"世界现在是什么样"必须有不同的、且受控的认知。狼知道同伴是谁，预言家知道验过谁，村民什么都不知道，而这三份认知必须来自同一个世界。

于是问题从"怎么编排"变成了"世界是什么样，这件事能有几个说法"。一个典型实现里，它至少有四个说法：引擎里的状态字段是一份，拼提示词时手写的那段描述是一份，校验模型输出时的那段判断是一份，跑完之后统计脚本重新解析日志又是一份。四份各自演化，谁也不保证一致。

能观察到的症状是这样的：提示词告诉模型"你可以救人"，模型照做，执行层拒绝，因为解药已经用掉了——两处各写了一遍规则，改了一处忘了另一处。或者更糟：某一局狼人精准地投出了预言家，没人能说清是推理还是泄露，因为"狼能看到什么"这件事没有唯一的定义点。

§2控制流索引在路径上，还是索引在状态上

在动手之前先确认过这个轮子该不该造。图编排类框架（LangGraph 一类）把控制流表达成图，对抗环境类项目（TextArena 一类）提供的是环境集合、目标是给模型排名。前者的问题不在于表达能力，而在于分支挂在什么上面；后者的问题是把环境当作固定资产，新增环境、替换规则参数、把真人塞进某个座位都要改它的内部。

先说前者，因为那才是结构性的分歧。

分支的索引方式决定规则的复制次数

自动机理论里这组区分早有名字：Mealy 机的输出取决于（当前状态，这条转移），Moore 机的输出只取决于当前状态。图编排的条件边天然是 Mealy 的——路由函数的名字里就带着"从哪个节点来"（route_after_night、route_after_vote）。

这个区分在对抗游戏里立刻变成可数的代价。这套规则里能致死的路径有六条：夜刀、女巫毒、同守同救抵消、白天票出、狼自爆、猎人开枪。而死亡的后果有三条：猎人要开枪、警长要传警徽、够条件的人要留遗言。

Mealy 式的写法里，每一个可能死人的节点后面都要挂一条条件边，而每条边都得把三个后果问一遍。六个来源乘三条后果，是十八处判断；再加第四条后果，要在六个路由函数里各补一遍。更麻烦的是这十八处之间没有任何机制保证一致：把"被女巫毒死的猎人不能开枪"这条改动漏在其中一处，程序不报错，只会打出一局"夜里毒死能开枪、白天票出不能开枪"的怪棋。

Moore 式的写法把分支挪到状态上。六条致死路径全部经过同一个函数 _kill(seat, cause)，它记录死亡，然后由 _queue_deaths 判断三条后果——写一遍。调度函数 _next() 不知道刚才发生了什么，也不需要知道，它只读当前状态：狼死光了吗、有待处理的插入回合吗、现在是什么阶段。夜里被毒死的猎人和白天被票出的猎人走到这里时是同一个状态（_pending_hunter 有值），因此只需要一次判断。六加三，是九处；加第四条后果，改一处。

乘积塌成求和的原因是所有路径在写状态的那一刻汇合了。图编排里没有这个汇合点——状态虽是共享字典，控制流却不共享，所以判断必须在每条出边上重来一遍。

汇合点的代价

这不是免费的。Moore 化意味着把"隐含在控制流里的信息"显式化成状态：_pending_hunter、_pending_badge、_pending_last_words、_settle_to 这些字段之所以存在，纯粹是为了记住"接下来该干什么"——Mealy 机不需要它们，那个信息藏在"程序正走在哪条边上"这个事实里。本质是拿存储换分支数。

更要紧的是，整个论证建立在一个前提上：所有死亡都必须真的经过那个漏斗。只要有一处直接写了 self._alive.discard(x)，后果规则对那条路径就静默失效——不报错、不崩溃，只是那种死法的猎人不开枪。语言本身不强制这件事，Java 的 private 同样不强制（它挡的是类外，而绕过发生在同一个类的兄弟方法里）。

这个项目最终把它做成了结构约束而非纪律：存活集合的类型是 frozenset，discard() 这个方法根本不存在，误写时得到的是 AttributeError 而不是静默旁路；能整体重新绑定它的位置由一条解析源码的测试限定在 _kill 与 reset 之内。两者合起来，等价于 Java 的"不可变视图 + 代码审查"，只是审查是自动的。值得记下的是：这条约束加上去的当天就抓到一处违规，而它出现在项目自己的测试代码里——为了构造一个"已出局的座位"而直接改了存活集合。为省事而绕过漏斗，正是这一设计最容易被破坏的方式。

这里为什么值得这样做

把判断从边上挪到状态上，代价是显式化的状态字段（见上）。这笔交易划不划算，取决于一个问题：

同一类后果，有没有多条路径能触发？本环境中有：六条致死路径对三条后果，且后果之间还能连锁——猎人的枪可以打死另一个猎人。判断挂在边上时代价是乘积，挂在状态上时是求和；后果每增加一条，前者要改六处，后者改一处。反过来，若流程本身是线性的——解析、切片、入库、检索、生成——就不存在需要汇合的多条路径，把判断留在边上不但够用，还能给出一张可以看的图。

这一选择在本环境中付出的具体代价有三项：

代价具体表现
流程不可视没有图。要知道"投完票之后会发生什么"，须读进 step、再进 _settle_if_clear、再进 _next。图编排能直接给出一张图，这在向他人解释系统时是实打实的优势。
状态更厚七个字段纯粹用于记录"接下来该干什么"；它们要在重置时初始化、在重放时被覆盖，改规则时容易漏掉其中一个。
漏斗需要额外的强制手段语言不保证唯一入口，需要 frozenset 加一条解析源码的测试来补。这部分工作在图编排里不存在。

§3信息可见性：权限作为构造，而非检查

上一节的分歧关于控制流。第二处分歧关于信息可见性，而它同样不是实现风格之争——两种做法把权限放在了不同的位置：一种把它做成访问时的判断，另一种把它做成交付时的构造。

视图的三层结构

第二处分歧关于信息可见性，而它的核心是 observe(actor) 返回的那个字典长什么样。它有三层：

view ├── you / role / round / phase … 你自己的基本信息 ├── public 公开层——所有座位拿到的内容完全一样 │ alive、dead、speeches、votes、exiles、sheriff … └── private 私有层——因角色而异 my_actions 人人都有：你自己做过什么 fellow_wolves 只有狼有 checks 只有预言家有 antidote_available 只有女巫有

公开层与私有层的划分本身不新鲜；关键在于这个划分发生在哪一步。它发生在取数时，而不是渲染时。一个村民座位拿到的 private 里只有一个键，一个狼座位拿到的有九个——差异已经体现在数据结构上，而不是留给下游去判断。

渲染层不再承担权限判断

把状态摊给每个节点的设计里，拼提示词的函数承担两件事：先判断"你是谁、你能看什么"，再把结果渲染成文字。两件事交织在一个函数里，而它有全局视角，所以两件事都必须由它做对。

权限判断在渲染层
def build_prompt(state, seat):
    role = state["_roles"][seat]     # 先判断你是谁
    lines = [公共部分]
    if role == "werewolf":           # 再决定给你什么
        lines.append(f"同伴：{找出所有狼}")
    return "\n".join(lines)
权限判断在取数层
def system_message(view, ...):
    priv = view["private"]
    lines = [f"Alive: {view['public']['alive']}"]
    if "fellow_wolves" in priv:      # 有就渲染，没有就跳过
        lines.append(f"同伴：{priv['fellow_wolves']}")
    return "\n".join(lines)

右侧那个条件判断的是字典里有没有这个键，不是"你是不是狼"。"狼才能看到同伴"这条规则完全不在渲染层——它在 observe 里，而它作用的结果就是那个键在不在。渲染层甚至不需要知道游戏里有"狼"这个概念，它只把手上有的东西翻译成文字。

这个拆分之所以要紧，是因为渲染有很多种，权限判断只有一种。同一份视图要被拼成给模型看的提示词、渲染成给真人看的网页、序列化成给观战者的 JSON。三种渲染，三份代码；如果权限判断留在渲染层，就是三处可能写错的地方，而且真人那条路要把整套过滤重做一遍。本项目里没有为真人写过一行过滤代码——真人坐第三个座位，拿到的就是 observe(3)，和模型坐在那里拿到的是同一个字典。这才是"玩家是可替换组件"的实际含义：换一个玩家实现，不需要重新证明隔离。

工具不是第二条信息渠道

智能体除了提示词还有工具（查询历史发言、查询票型等），这看上去像是绕过视图的另一条路。它不是：工具的执行上下文 ToolContext(view, belief, task) 只装了视图和智能体自己的笔记，没有环境对象。工具因此不增加信息，只是分页——历史发言一直在视图的公开层里，只是没有全部铺进提示词（那样太长），需要时用工具翻出来。视图里没有的东西，任何工具都变不出来。

以上三小节说明了这套做法是什么。它并非新技巧：这类做法有名字，也有四十年的先例，而与之相对的另一类做法正是被广泛采用的那一种。

把权限做成检查，是一种做法：调用方来取数据，系统判断"你有没有资格"，然后放行或拒绝。这是访问控制（ACL）的思路，文件系统的读写位、接口上的鉴权中间件都属于此类。把权限做成构造，是另一种：系统交给调用方一个已经受限的对象，调用方对它拥有全部权限，而不该看的东西根本不在这个对象里。这是能力式安全（capability-based security）的思路，Unix 的文件描述符是它最常见的例子——拿到描述符就能读，没拿到则连"读哪个文件"这句话都说不出来。

访问控制

调用方发起访问 → 系统检查「你有权限吗」 → 放行 / 拒绝

权限是行为。每个访问点都需要一次判断，判断本身可能被遗漏、被写错、被绕过。

能力式（本设计）

系统构造一份受限对象 → 交给调用方 → 调用方对它有全部权限

权限是数据。没有访问点，因此没有判断，因此没有可遗漏的判断。

本设计中的 observe(actor) 属于后者：它不判断"这个座位能不能读全场身份"，它构造一个不含全场身份的世界并交出去。座位在那个世界里享有百分之百的权限，因为凡是它不该知道的，都已经不在世界里了。

由此得到的四项性质

其一

没有检查，就没有"忘了检查"。访问控制的每一个检查点都是一处可能遗漏的地方，而检查点的数量随功能增长。这里的检查点是零——不是检查得仔细，是这个动作不存在。本节末记录的那次真实泄露恰是反证：那个接口是访问控制式的（先取全部数据，再想起来应当过滤），所以漏了；修复方式是把它改成能力式，即按可见性构造出该给的那一份。

其二

下游可以做得很笨。世界既已裁剪完毕，消费者就不必理解规则。渲染层那句"字典里有这个键就渲染"正是如此——它不知道游戏里有"狼"这个概念。若采用访问控制，每个消费者都要自己判断一次"这个座位是不是狼"，于是每个消费者都得懂规则，规则也就随消费者数量复制。

其三

发出去的东西可以被检查。视图是数据：可以序列化、可以遍历、可以断言。而"某个检查若被触发是否正确"不是数据，是行为，无法用同样的方式验证。隔离测试之所以能存在，前提就是权限以数据形态存在。

其四

玩家可以由第三方实现。第三方写一个 act(view, task, spec, feedback)，想作弊也没有可作弊的对象。访问控制则需要审查第三方代码有无绕过检查的路径——而这在多智能体基准里几乎是不可能完成的审查。

代价

要为每个参与者构造一份世界。每个回合至少构造一份，观战与网页渲染时还要再构造；构造出的是拷贝，有内存与计算成本。本项目规模下可以忽略，规模更大时需要惰性构造或结构共享，而结构共享又会削弱"拷贝不可被就地修改"这一性质——这是需要权衡的地方，本项目选了简单。

公开信息在各份世界之间重复。同上，可以用共享引用消除，代价同上。

构造函数成为单点。它不防止错误，只是使错误局部化并可被机械检查（见本节末）。

可检查性

需要说清楚的是：这个设计并不能阻止开发者写错。若有人在 observe 里加一行把全场身份塞进视图，泄露照样发生。真正的差别在别处，有两条。

其一，错误只可能出现在一个地方。摊开状态的设计里，任何一个拼提示词的节点都可能泄露，而节点数量随功能增长；这里能决定谁看到什么的只有 observe 这一个函数。审查范围从"所有渲染代码"缩成几十行。

其二，也是更要紧的，泄露的形态从自然语言变成了数据结构。在渲染层泄露，产物是一句话，而且可以是转述的——不必写"三号是狼"，写"你的同伴很可靠"就够了，没有任何自动化手段能检查一段散文是否隐含泄露。在取数层泄露，产物必然是字典里多出的一个键或一个值，而字典是可以遍历、可以断言的。本项目的隔离测试正是这么做的：跑完整局，对每一个回合的每一个座位，把视图序列化后断言其中不出现他人的角色。

这条保证的边界也应当写明。它成立的前提是提示词只由视图派生——渲染函数与玩家的签名里都没有环境对象，因此这条链是闭合的。但它只保证"实现符合设计"，不保证"设计正确"：若规则本身被设计成让村民看到女巫的用药情况，测试照样通过。

更值得记下的是这条保证漏掉的地方会发生什么。本项目一度提供一个读取完整对局记录的接口，它不经过 observe，直接从日志渲染——于是活着的玩家在对局进行中可以读到每一次夜间行动。写这个接口的人（也就是把隔离当作核心卖点、并为此写了整套测试的人）照样漏了，且数日未察觉，因为那套测试检查的是 observe 的输出，而这条路径绕开了它。修复方式是让该接口走同一道门。这件事同时说明两点："记得小心"确实靠不住；而收口的价值不在于让人不犯错，在于犯错之后问题必然属于同一类——某处绕开了那道门——因而定位是分钟级的。

这里为什么值得这样做

构造式的代价是为每个参与者造一份世界（见上）。这笔交易划不划算，取决于一个问题：

参与者之间是否存在信息差，且是否有动机利用它？这是本文全部论证中最具决定性的一条，因为这两个条件各自决定了一件不同的事。

信息差决定了有没有东西要过滤。若所有参与者本就共享同一份信息——多数协作型流水线正是如此——那么"泄露"这个概念不成立，构造式没有任何可省的东西。

动机决定了错误能否被发现。若有信息差而无人有动机利用它，多发出去的字段最坏只是浪费 token：这是效率问题，且随时可以从日志和账单上看出来。一旦存在利用动机，泄露的性质就变了：它不抛异常（多一个键、多一句话都是合法数据）；它的后果与正常表现无法区分（狼精准投出预言家，可能是推理，也可能是看了底牌）；它也读不出来（泄露可以是转述的——不必写"三号是狼"，写"你觉得三号今天有点闪烁"就够了）。这类错误是不可观测的。

而不可观测的错误无法用事后检测来防守。访问控制式的做法本质上是事后检测路线——它假定判断写错了会被发现；构造式是事前排除路线——不该看的东西不在交出去的对象里，"判断错"这个动作不存在。它同时把检查对象从行为换成了数据：不是检查"那个判断有没有写对"，而是遍历发出去的视图断言其中不含他人身份。前者查不了，后者跑一遍就行。

反过来，若场景中不存在信息差，或存在信息差但无人有动机利用，访问控制更省事，构造式纯属多绕一层。

§4公理及其推论

世界状态私有于环境对象，且存在且仅存在一个函数 step(actor, task, action) 能修改它。
智能体持有的一切——观察、动作清单、反馈——都是 step 之外的函数从状态派生出来的副本，不是状态本身。

这句话看上去平庸："状态当然是规则决定的"。但它管的不是"谁决定"，是"谁有资格让世界前进"。

这个项目里真出过一个正好踩线的缺陷。有个函数叫 _chat_speaker()，作用是"现在轮到哪只狼说话"——名字是个查询，实现里却顺手把轮次游标加了一。于是每多调用它一次，讨论就往前推一轮：前端刷新一次页面可能推一轮，重放日志时调用次数与原来不同，重建出来的就不是同一个世界。规则一个字没变，失控的是"什么时候算走了一步"。

公理成立时，observe 调一万次世界纹丝不动，而世界每前进一步都恰好对应日志里的一条 step。一局 12 人局录下来是：读 603 次、问玩家 201 次、写 201 次，日志正好 201 条。

两个维度，同一种构造

§3 说的是"你能看到什么"。同一种构造方式还作用在另一个维度上——"你能做什么"。

认知边界
observe(actor)
  → 你能看到的世界
能力边界
action_space(actor, task)
  → 你能做的动作集

女巫没有解药时，"救人"不是被判为非法——它不在动作清单里。守卫不被允许守护自己时，他自己不在目标名单里。两者与视图遵循同一条原则：不是"你申请、我审批"，而是"我造好交给你，交出去的就是全部"。因此隔离与合法性并非两条独立的性质，而是同一种构造方式分别作用于"知道什么"与"能做什么"的结果。

这也解释了规则参数为什么必须是数据：guard_self 这一个布尔值同时决定目标名单里有没有自己、以及规则文本里那句话怎么写。一条规则，两个出口，同一个源头——一个出口通向能力边界，一个通向认知边界，同源因此不可能互相矛盾。

规则以数据形式存在一处

上一段的 guard_self 说明了一件更一般的事：凡是有两个以上消费者的规则，都必须写成数据。step 读它执行，rules_text 读它渲染给模型看，测试读它构造断言；改数据三处同变，只改引擎不改数据则测试失败。"改了代码忘了改提示词"这类缺陷因此被消掉。

需要说明的是这条约束做到什么程度取决于消费者数量，而非越彻底越好。行为规则有两个消费者（引擎与规则文本），所以抽成了 Variant 的字段；可见性规则只有一个消费者（构造视图那一次），因此留在 observe 的代码里，没有抽成配置表。若哪天要把"狼互相知道身份"写进给模型看的规则文本，它就有了第二个消费者，那时才该抽。抽象过度与抽象不足同样是成本。

确定性

world == f(seed, journal)。世界完全由种子与动作日志决定：中断的对局可以重放接续且重放不询问模型，A/B 实验可以用同一副牌跑两套规则做配对，缺陷可以精确复现到第 N 个回合。这条性质本身直接来自公理——若存在 step 之外的状态写入，日志就不再是完整的输入序列。它与图编排的检查点机制如何取舍，是下一章的内容。

§5持久化：记录状态，还是记录动作

确定性的用途——重放、断点续跑、同种子对照——在图编排框架里也有对应物：检查点（checkpointer）。两者解决同一个问题，做法却相反。这一节把它们并排放好，并说明这个场景为何选了后者。

快照式：图编排的做法

图编排框架在每个超步（super-step，一次调度中所有节点的并行执行）之后写一份检查点。一份检查点里装的是状态本身：通道值（channel_values）、通道版本（channel_versions）与版本可见性记录（versions_seen）；外层还包着线程与检查点标识、元数据、本超步内已完成节点的中间写入（pending_writes），以及指向父检查点的引用。

恢复的语义是：检查点之前的节点被跳过（结果已在快照里），之后的节点重新执行。为容错，超步内单个节点失败时，同超步已成功节点的写入会被保留，恢复时不重跑它们。

日志式：本设计的做法

这里不存状态，只存动作。日志的每一条就三样东西：谁、做什么任务、做了什么。恢复时用同一个种子重新发牌，再把动作依次喂回 step：

def replay(env, seed, journal, upto=None):
    turn = env.reset(seed)                                    # 同种子 → 同样的初始状态
    for rec in journal[:upto]:
        assert (turn.actor, turn.task) == (rec.actor, rec.task), "日志对不上"
        turn = env.step(rec.actor, rec.task, rec.action)       # 动作从日志读，不问模型
    return turn

正常对局时 step 的第三个参数来自模型，重放时来自日志；除此之外走的是同一套规则与结算。世界因此是种子与日志的函数，重放不过是对同一串输入的一次折叠。

不构成差别的部分

两点常被误当作差别，应当先排除。

其一，"恢复时不必重付前缀的代价"两者都做得到。图编排跳过已完成节点，本设计重放时不调用模型，在省钱这一点上没有分别。

其二，两者都支持中途接管。人工介入、从中间某点继续，都不是任何一方独有。

四处真正的差别

其一 · 存下来的东西有没有意义

日志是 (谁, 做什么, 做了什么) 的序列，它同时就是这局对局的记录本身：统计兜底率、做同种子配对、审计某个模型在第几回合做了什么判断，用的都是它。快照存的是运行时内部表示，能恢复执行，但不能直接回答"这局发生了什么"。

其二 · 体积与增长

快照每个超步一份，长线程上会持续增长；官方文档为此提供了增量通道（DeltaChannel），只存增量以压缩体积。日志每回合一行，而那一行本就是模型返回的 JSON——它天然可序列化，不需要额外的序列化约定。

其三 · 失效时的表现

两者都会因"被恢复的东西与当前代码不匹配"而失效：快照绑定图结构与通道版本，日志绑定规则。差别在于失效如何暴露。日志式重放每一步都断言"环境认为该谁行动"与"日志记录的是谁"一致，不一致当场停下并指出第几步分叉；它不会悄悄重建出一个不同的世界。

其四 · 重放会不会重新产生副作用

图编排的文档明确指出：中断在重放时总会被重新触发，若配置了人工审批，恢复时需要重新审批一次。这是快照式的固有性质——检查点之后的节点要重新执行，那么这些节点的副作用也会重新发生。日志式重放不重新执行任何外部动作，因为动作的结果已经在日志里；重放只是把它们重新应用到状态上。

代价：日志式要求确定性，快照式不要求

这是快照式实打实的优势，必须写明。快照记录的是"状态成了什么样"，因此节点内部是否确定无关紧要——调了外部服务、用了时间戳、模型温度不为零，快照照样存得住、恢复得了。日志式记录的是"做了什么"，要从它重建状态，就必须保证同样的动作作用在同样的状态上得到同样的结果；任何非确定性的来源都不能进入状态转移。

另有一处量级上的取舍：日志式恢复是重新计算，代价随步数增长；快照式是反序列化，代价随状态大小增长。步数多而状态小的系统，日志式吃亏。本环境每局约二百回合、状态数十个字段，重放一百多个回合耗时不足一秒，因此这一项不构成约束。

这里为什么选日志式

其一，产出要当数据用。这个环境的目的不是打完一局，而是产出可统计的记录。日志既是存档又是记录，两者本来就是同一份东西；若采用快照，仍需另外维护一份对局记录，于是又出现了两个必须保持一致的来源——正是 §1 所述的那类问题。

其二，要审计的是过程而非结果。"这个模型在第 137 回合做了什么判断、依据是什么"，快照答不了，它只说得出那一刻状态是什么样；日志逐条记着谁做了什么，配合每步的推理字段可以直接读。

其三，确定性在这里是本来就要的东西。日志式的前提（转移必须确定）对本设计不是额外负担——公理已经把状态写入收敛到 step 一处，而规则本身不依赖时间与外部服务。前提免费，代价便只剩重算，而重算在这个规模下可以忽略。

反过来，若节点会调用外部服务、状态里存着不可重现的东西，或者流程只需恢复执行而不需被审计，快照式是更合适的选择——它不要求你放弃非确定性。

§6三处与常规做法相反的取舍

身份是编号，行动能力是对象

环境里的一切都用座位号称呼参与者，而"能做出动作的那个东西"是另一个对象，由驱动循环用编号去查表拿到。直觉上应该合并成一个玩家对象——但一旦合并，环境就持有了智能体的引用，"环境只通过 observe 供给信息"这条就没有了强制力。分开的代价是多一次查表，换来的是隔离从约定变成结构。

step 返回下一个轮到谁

更常见的写法是把"下一步是谁"做成独立方法。但刚改完状态的那个函数最清楚下一个是谁；拆出去就等于让"下一步"有了第二个来源，两个函数读同一份状态各推一遍，迟早分叉。代价是 step 的职责变重，收益是控制流只有一处。框架因此不知道"投完票就到晚上"——它只是把 step 返回的东西喂回循环。

非法动作作为对话的一部分

模型给出非法动作时，校验返回的是理由字符串，这个理由回灌给模型让它重试。三次仍不合法才使用环境定义的兜底动作，并标记该回合。标记是必须的：兜底动作本身合法，不标记的话日志就把系统代打记成了模型的判断，之后基于日志的一切分析都建立在假数据上。

§7有意省略的部分

没有理由
图 / DAG控制流由状态决定，不是预先声明的。声明一份就等于给"下一步"加了第二个来源。
检索式记忆单局上下文长度可控，历史发言可由工具按需查询。引入向量检索会在评测里多一个不可控变量。
沙箱工具全部是对本局状态的纯查询，不触碰外部世界。没有需要隔离的副作用。
运行时的通用能力Layer A 不含重试策略、不含日志格式、不含并发模型。这些是使用者的选择，写进框架就成了所有人的约束。

§8为什么以狼人杀为载体

前面各节论证的是设计本身。但一套设计只能在它被检验过的场景里被相信，因此有必要说明：这个载体是怎么来的，它压到了哪些地方，又有哪些地方它压不到。

它不是被挑出来的，是起点

诚实地说，这里没有"先确定研究问题、再挑选合适基准"的过程。项目最初就是一个狼人杀对局程序；本文所述的这层契约，是在那个程序变得难以维护之后从中抽出来的——引擎一份规则、提示词一份规则、校验一份规则，三份各自演化，于是才有了§1 的问题陈述。论证的顺序与发生的顺序相反，这一点不应当被叙述掩盖。

但这不妨碍事后判断它是否合适。§2、§3 与 §5 各自记录了三处选择在这个场景下为何值得；此处补充两点便利，以及它检验不到的地方。

两点便利

真人可以坐进去。这是检验"玩家是可替换组件"最直接的方式：一个人坐进第三个座位，收到的必须与模型收到的完全一致，否则要么泄露、要么不公平。这条约束若不成立，隔离就只是纸面性质。

领域知识为零。规则是常识，读者不需要背景就能判断"这个座位不该看到那个信息"是否成立。换成供应链博弈或金融撮合，论证同样成立，但读者要先学一套领域术语才能验证它。

它检验不到的地方

把边界写清楚，否则前面的结论会被读成比实际更强的东西。

未被检验原因
沙箱与副作用隔离本环境的全部工具都是对本局状态的纯查询，不触碰外部世界。真实智能体系统里的工具会写数据库、发请求、花钱，那类隔离本设计一行未写。
长程记忆与上下文压缩单局上下文长度可控，历史发言按需检索即可。需要跨会话记忆的场景，这里没有任何证据。
分布式与并发一致性一局一个线程，状态在进程内。多进程共享一个环境时公理如何维持，本设计未做回答。
规模最大十五个座位、每局约二百回合。参与者数量再高一个量级时，"为每个人构造一份世界"的开销是否仍可接受，未经验证。

换言之，本文的结论限于回合制、进程内、参与者数量在十几量级、工具无副作用的对抗环境。超出这个范围的部分，本项目没有提供证据。

§9两项已被推翻的论断

把这一节写进来，是因为设计过程里最有价值的部分往往是被否掉的那些。

收回其一 · 论证方式

最初为"隔离必须由框架保证"给出的理由是：有人可能写错——某个提示词拼装函数为省事直接读取了全场身份。

不认可，你不能假设有人写错，只要框架本身可以保证狼人看不到不该看的东西即可了。—— 项目过程中的原话

这个反对是对的，而且比原来的理由更强。"怕人写错"是概率论证，靠的是纪律；"结构上不给机会"是构造论证，靠的是类型和可见性。observe 返回副本、状态私有、玩家拿不到环境引用——这三件事一起使得想泄露也没有渠道。公理的最终形式来自这次反对。

收回其二 · 一个多余的分类

曾把规则分成两类：参数型（能触发开枪的死因集合、投票能否弃权）写成结构化数据，逻辑型（同守同救不抵消、平票无人出局）只能是代码。并据此设计了两套处理方式。

我没懂的地方是，现在无非是要不要把句子写死……所以我没懂这里分成两种的意义在哪。—— 项目过程中的原话

确实没有意义。两类规则要的是同一件事：只写一遍，三处引用。参数型引用的是数据结构，逻辑型引用的是同一个函数——差别只在被引用的东西长什么样，不构成两种设计。这个分类被删掉，关于规则数据的那一节从两段合并成一句。

顺带删掉的还有一个自造词。原先把"从规则数据构造断言的测试"叫作探针测试，被指出这就是普通测试，没必要造名词。造词会让读者以为有新机制，是纯粹的损耗。

§10契约层的规模

两项与机制无关的代价

以上各章分别记录了每处选择自身的代价。还有两项与具体机制无关，属于自研运行时的固有成本。

没有生态。检查点、链路追踪、可视化调试器，全部自行实现。

无人认识它。三百五十八行是自己的三百五十八行：新人要读完才能改，而某个通用框架的新人可能已经会了。这一条在真实团队中往往权重最高，也最容易在技术论证中被忽略——若团队已在使用某个编排框架、而场景又属于协作型，直接沿用它是更好的选择。

Layer A 是 358 行：环境暴露五个方法，玩家暴露一个方法，step 的返回是"下一个轮到谁"或"结束了"的联合类型。整个驱动循环是十七行。

薄本身不是目的，可验证才是。一层薄到能被完整覆盖的契约，才能说"隔离由框架保证"而不是"由使用者遵守"。换一个对抗场景——拍卖、谈判、多方博弈——重写的是规则层；这十七行不动。

这也是它与编排框架的分工：编排框架解决"多个步骤怎么串起来"，这层解决"多个参与者对同一个世界的认知怎么受控地分发"。前者的答案是图，后者的答案是一条公理和四条从它推出来的性质。

0开场：这个框架是什么

被问「先介绍一下项目」时的一分钟版本。

一个跑「多个智能体在有规则的对抗环境里轮流行动」的运行时。契约层 358 行，驱动循环 17 行。环境暴露五个方法，玩家暴露一个：

方法管的事防的是什么
observe(actor)你能看到什么「谁能看什么」有第二个定义点
action_space(actor, task)你现在能做什么提示词和校验各写一份规则
step(actor, task, action)世界怎么前进，顺便返回下一个该谁状态多点写入；「下一步」有第二个来源
reset(seed)初始状态配合 step 才有 world == f(seed, journal)
rules_text()给模型看的规则手写第二份规则
act(view, task, spec, feedback)玩家唯一方法，签名里没有环境对象越权在类型上没有渠道

为什么这样切：对抗任务和协作任务的差别只有一条——参与者对世界的认知必须不同且受控。协作里大家共享状态，编排框架把状态摊给每个节点没问题；对抗里一摊就泄露，而且泄露不报错、不可观测。所以重心从「怎么串流程」换成「谁有资格知道什么、做什么、改什么」，三个问题对应三个方法。

追问：为什么不用 LangGraph

不要答「它不行」，答「它适合什么、这里不是那种情况」。三项判据，每项对应后面一条：

  • 参与者之间是否存在信息差，且有动机利用它？有 → 可见性要做成构造（第 1 条）。
  • 同一类后果是否有多条路径能触发？有 → 控制流索引在状态上（第 4 条）。
  • 状态转移是否由框架拥有且确定？是 → 持久化记动作而非记状态（第 3 条）。

三条都不满足的场景——线性流水线、信息共享、节点调外部服务——LangGraph 是更好的选择，而且它有生态、有人认识。这句要主动说。

1可见性：三层视图

针对对抗任务中不同 agent 可视环境不同的问题，设计三层视图结构，输出一份针对不同角色裁剪后的环境，大大简化了权限判断流程，保证了不同 agent 的上下文隔离。

它在说什么

observe(actor) 返回一个字典，三层：you（自己的基本信息）、public（所有座位拿到的完全一样）、private（因角色而异）。村民的 private 里只有一个键，狼有九个。差异在数据结构上，不留给下游判断。

渲染层因此不含角色概念。它写的是 if "fellow_wolves" in priv，不是 if role == "wolf"——有这个键就渲染，没有就跳过。「狼才能看到同伴」这条规则只在 observe 里。

追问：这和普通的权限判断有什么区别

两种放法。访问控制：调用方来取，系统判断「你有没有资格」，放行或拒绝——每个访问点一次判断，判断可能漏、可能错。能力式：系统交给你一个已经受限的对象，你对它有全部权限，不该看的根本不在里面——没有访问点，所以没有判断，所以没有可漏的判断。Unix 的文件描述符就是后者：拿到就能读，没拿到连「读哪个文件」都说不出来。

追问：开发者写错了不照样泄露吗

对，这个设计不阻止写错。差别有两条。其一，错误只可能出现在 observe 一处，审查范围从「所有拼提示词的代码」缩成几十行。其二，泄露的形态从自然语言变成数据结构——在渲染层泄露可以是转述的（「你的同伴很可靠」），没有自动化手段能查；在取数层泄露必然是字典里多出一个键，可以遍历、可以断言。隔离测试就是这么做的：跑完整局，对每个回合每个座位序列化视图，断言不含他人角色。

可以主动讲一次真实的漏：项目曾提供一个读完整对局记录的接口，它不经过 observe，直接从日志渲染，活着的玩家在对局中能读到每次夜间行动。写隔离测试的人自己漏了，数日未察觉。修法是让该接口走同一道门。这件事说明「记得小心」靠不住，也说明收口的价值：犯错之后问题必然属于同一类，定位是分钟级的。

追问：工具不是另一条信息渠道吗

不是。工具的执行上下文 ToolContext(view, belief, task) 只装视图和智能体自己的笔记，没有环境对象。工具不增加信息，只分页——历史发言一直在视图的公开层里，只是没全铺进提示词。

追问：真人怎么坐进去

真人座位实现同一个 act，内部用队列和超时代替提示词和补全。拿到的就是 observe(3)，和模型坐那里拿到的是同一个字典，为真人没写过一行过滤代码。这是「玩家是可替换组件」的实际含义：换玩家实现不需要重新证明隔离。

追问：LangGraph 里不能写死只读某些字段吗

能，而且通常就是这么做的：

def villager_node(state):                      # state 是整个字典，roles 在里面
    view = {k: state[k] for k in ["alive", "speeches"]}   # 只挑这几个
    ...

这段代码是对的。问题在三处。其一，门在消费者那边：state["roles"] 这个表达式写得出来，没被写是因为写代码的人没写。三个月后有人为了「告诉村民场上有几只狼」顺手从 roles 里数了一下，程序照跑、测试照过。这边视图里没有 roles 这个键，同样的改动是 KeyError，只能去改 observe，而 observe 有隔离测试守着。其二，有多少节点写多少份：村民、预言家、女巫、网页渲染、观战序列化各挑一遍字段。其三，写错了查不出来：没有断言能检查「某个节点读了不该读的字段」。

一句话：LangGraph 里不该看的东西在手边，不看靠自觉；这边不该看的东西不在手边，想看会报错。LangGraph 自己也有更接近的做法，给子图定义独立 state schema 加映射函数，那个映射函数就相当于 observe，但它是可选的，默认整个字典往下传。

追问：为什么值得多绕这一层

取决于两个条件。信息差决定有没有东西要过滤——协作流水线里大家共享信息，「泄露」这个概念不成立。动机决定错误能否被发现——有信息差无人利用，最坏是多花 token，账单上看得出来；一旦有人有动机，泄露不抛异常、后果和正常表现无法区分（狼精准投出预言家，是推理还是看了底牌？）、也读不出来。这类错误不可观测，事后检测防不住，只能事前排除。反过来两个条件不满足时，访问控制更省事。

不要说

  • 「防止模型作弊」——模型手里没有环境对象，它作不了弊。防的是开发者自己。
  • 「靠提示词告诉模型不要提到不知道的事」——那正是这个设计要替代的做法。

2合法动作集

每回合由当前环境状态推出该角色的合法动作集，同一份动作集既渲染为模型看到的工具 schema、又作为执行前的校验依据，校验只做「是否在集合内」的通用判断、不重写任何规则。规则因此只在一处定义，避免了常见做法中提示词与校验各写一份、改一处漏一处的问题。

它在说什么

女巫救人的例子。第 2 夜，解药还在，受害者是 5 号。action_space(女巫, "night_save") 返回一个对象：工具名 night_save，参数 target_id，可选值 [5]。这个对象走两条路：

  • 转成 function-calling 的 JSON 给模型看，enum 是 [5]。
  • 模型答 night_save(3)，执行前用同一个对象 spec.check(action)，发现 3 不在 [5] 里，返回一句理由回灌给模型。

第 3 夜解药用掉了，action_space 根本不返回这个工具：schema 里没有，校验也拒绝，两边自动一致。每个动作的可选值都是从状态现算的：狼刀是活人减狼，查验是活人减自己减验过的，守护是活人减昨晚守的、guard_self 关则再减自己。死人自动从所有清单消失。

追问：检查逻辑不还是要写吗

要写，但它里面没有游戏规则。check 做的是「模型选的值在不在清单里」，对救人、毒人、投票、守护全通用，写一次。「只能救今晚的受害者」「解药用完不能救」这些规则只写在算清单的那一个函数里。规则变了清单跟着变，检查代码不动。

追问：这不就是 action mask 吗

是。RL 环境早有这个东西：Gym 的 action space、OpenSpiel 的 legal_actions()、PettingZoo 的 mask。主动承认。差别在于 RL 里策略网络直接吃 mask，不需要「渲染给模型看」这一步；Agent 框架里工具列表是静态绑定的，没有按状态现算合法集的概念。这里做的是把两边接起来：同一个对象既是 schema 又是校验器。

别人怎么做

做法告诉模型能做什么检查模型做的对不对
LangGraph 静态绑定建图时 bind_tools([...]) 一次，每轮模型看到同一份列表，解药用完了 night_save 还在进到工具函数体才判断，if not antidote_left 再写一遍规则
Instructor / Guardrails不管，提示词自己写校验回复是否符合 Pydantic 模型，查类型不查状态
TextArena 类游戏基准手写一句「你可以投给 1、3、5 号」正则抠出目标，再写代码判断

三种都是「告诉」和「检查」两段代码，规则改了要改两处。LangGraph 可以每轮重新 bind_tools 做到动态，但工具函数体里的判断仍然是另一段代码，因为它拿不到「模型看到的那个清单」。

不要说

  • 「引入动作空间的概念」「首创」——RL 里三十年前就有。
  • 「从根本上杜绝非法动作」——模型仍然可能选清单外的值，只是会被同一个对象拒绝并重试。杜绝的是「两份规则不一致」。

3唯一写入口与重放

设计统一的执行函数作为改变环境状态的唯一入口，避免多点写入导致的环境混乱。由于环境完全由初始状态和执行函数决定，中断后重放执行函数日志即可恢复到断点，简化了恢复步骤。

它在说什么

日志每条三样：谁、做什么任务、做了什么。恢复时同种子 reset，再把日志逐条喂回 step，第三个参数从日志读而不问模型。除此之外走的是同一套规则，所以重建出来的是同一个世界。一局因预算耗尽中断在第 135 回合，重放接续打完，重放段零模型调用。

追问：防的是模型乱改吗

不是。模型手里没有环境对象。防的是开发者在别处顺手改状态。项目里出过一个正好踩线的缺陷：_chat_speaker() 名字是查询「现在轮到哪只狼说话」，实现里顺手把轮次游标加了一。前端刷新一次页面推一轮，重放时调用次数与原来不同，重建出来的就不是同一个世界。规则一个字没变，失控的是「什么时候算走了一步」。公理成立时，observe 调一万次世界纹丝不动，12 人局录下来是读 603 次、写 201 次、日志正好 201 条。

追问：出错了怎么办

三层，按严重程度：

  • 单步非法：校验理由回灌给模型重试，最多三次。
  • 三次仍非法：环境给出最保守的合法动作并标记。标记是必须的，兜底动作本身合法，不标记的话日志就把系统代打记成了模型判断。连续 10 次兜底熔断作废，宁可丢局也不产出假记录。
  • 进程挂了、欠费、断网：每 25 回合自动落盘，从日志重放到断点。

这一段的完整调用栈见「纠错」tab：真实记录，可以逐步展开。

追问：LangGraph 有 checkpoint，区别在哪

它存状态，这里存动作。同一局 8 人 81 回合实测：快照累计 526,773 字节，相邻两份 97.7% 相同；日志 8,201 字节。但体积不是重点，重点是谁是权威：

权威来源换来的代价
LangGraph快照代码可以变，旧存档照样加载——存的是结果，跟产生它的代码无关存档不能直接回答「这局发生了什么」，要另维护一份记录
这里日志存档即记录，统计、配对、审计都用它；每步断言「该谁行动」与日志一致，不匹配当场指出第几步分叉要求转移确定；规则一改历史作废

为什么这里选日志：产出要当数据用，快照还得另存一份记录，又是两个来源；要审计的是过程不是结果；确定性本来就有——公理已把写入收敛到 step，规则不依赖时间和外部服务，前提免费。规则改了历史作废这一条可以接受，因为规则变了实验本就该重跑。

追问：只记 action 不记 actor 和 task 行不行

行，实测过，只喂 action 也能重放出同一局。actor 和 task 是刻意的冗余，作用是校验和：代码变了、日志对不上时，它让重放在第 N 步停下并说出原因，而不是悄悄重建出另一个世界。

不要说

  • 「LangGraph 不记节点输出」——它记，pending_writes 和 metadata.writes。它只是不把那个当权威。
  • 「快照慢」——这局规模下重放不到一秒，反序列化也不到一秒，性能不构成理由。
  • 「它不敢记动作」——原因是它不拥有状态转移（节点和 reducer 都是用户代码），不是不敢。

4控制流索引在状态上

设计以状态为索引的控制流，各条路径只负责写入状态，调度只依据当前状态决定下一步、不关心它是经哪条路径到达的，避免了相同的规则随触发路径增多而重复、漏改不报错的问题。

它在说什么

「下一步做什么」这个决定，查什么来做。按路径：查「我从哪条边过来的」，图编排就是这样，投票节点后面挂一个路由函数，夜晚节点后面挂另一个，每个只知道自己前面那个节点。按状态：查「世界现在什么样」，只有一个调度函数，它不知道刚才发生了什么，只读几个字段：有没有待开枪的猎人、狼死光了没、现在什么阶段。自动机里叫 Mealy 和 Moore，报这个名字就够。

可数的例子：能致死的路径六条（夜刀、毒、同守同救、票出、自爆、猎人枪），死亡后果三条（开枪、传警徽、遗言）。按路径写是六乘三，十八处判断，加第四条后果改六处；按状态写，六条死法全经过 _kill，后果只判断一次写进待办字段，六加三，九处，加一条后果改一处。

追问：为什么只看状态副本就少了

因为只看状态，就意味着所有路径在写状态的那一刻汇合了。六条死法做的都是「往状态里写一笔：某某死了」，写完之后它们的区别就消失了，调度看到的只是「有个猎人死了」。六条线汇成一条，判断自然只需要写在汇合之后那一处。副本数从「路径数 × 规则数」变成「路径数 + 规则数」——不是写法巧妙，是路径信息被丢掉了，丢掉之后没有东西可以区分它们，也就没有东西需要重复。

追问：我在 LangGraph 里加一个汇合节点不就行了

对，那就是这个设计，只是在图里手工搭出来。差别是图里那个汇合点靠纪律——没有任何机制阻止新加的路径绕过它直接改状态。这里把它做成结构约束：存活集合的类型是 frozenset，discard() 这个方法不存在，误写得到 AttributeError 而不是静默旁路；能整体重新绑定它的位置由一条解析源码的测试限定在 _kill 和 reset 之内。这条约束加上去当天就抓到一处违规，在项目自己的测试代码里——为了构造一个「已出局的座位」直接改了存活集合。

追问：积变成和，数学上怎么说

设触发路径集合 P，|P| = m；后果规则集合 R，|R| = n。按路径分支，每条路径上独立判断每条规则，判断点是 P × R 的每个元素，m·n 处；加一条规则要在 m 条路径上各加一处。按状态分支，所有路径先映射到同一个状态「某人死了」，判断挂在状态上，判断点是 P 的每个元素各写一次「写状态」加 R 的每个元素各写一次「判后果」，m + n 处；加一条规则只加一处。

能塌下来的条件：存在 f: P → S 把所有路径映射到同一状态，且规则只依赖 f(p) 不依赖 p。「猎人开不开枪」只取决于「有猎人死了」，不取决于「被毒死还是被票出」。条件不成立时，比如「被毒死的猎人不能开枪」，把路径信息写进状态（_kill(seat, cause) 的 cause），规则读 cause 字段，形式上仍是 m + n。

追问：「新增规则只改一处」具体指什么

现在死亡后果三条：开枪、传警徽、遗言。加第四条「死者若是守卫，公开他最后守的人」。按路径写，六种死法各有一段结算代码，每段加这个判断，改六处。按状态写，所有死法都进 _kill，_kill 后面调 _queue_deaths 判后果，在 _queue_deaths 里加一行，改一处。

追问：「静态检查」是什么

一条测试，不跑游戏，把 werewolf.py 当文本读进来，用 ast 解析成语法树，遍历所有给 self._alive 赋值的语句，断言它们只出现在 _kill 和 reset 两个函数里。谁在第三个地方写了 self._alive = ...，测试挂，不管那行逻辑对不对。配合 frozenset：就地改（.discard）报 AttributeError，重新赋值被这条测试抓，只剩 _kill 一条路。业界叫法是静态分析或架构测试，Java 圈的 ArchUnit 是同类。简历上写「静态检查」。

追问：代价

  • 状态更厚：_pending_hunter、_pending_badge、_pending_last_words、_settle_to 等七个字段纯粹用于记「接下来该干什么」。Mealy 机不需要它们，那个信息藏在「程序正走在哪条边上」这个事实里。拿存储换分支数。
  • 流程不可视：没有图。要知道「投完票会发生什么」得读进 step、再进结算、再进 _next。图编排能直接给一张图，向他人解释系统时这是实打实的优势。
  • 需要额外强制手段：语言不保证唯一入口，frozenset 加源码测试是补的，图编排里这部分工作不存在。

追问：什么时候不该这么做

流程本身线性时——解析、切片、入库、检索、生成——不存在需要汇合的多条路径，判断留在边上不但够用，还能给出一张能看的图。

不要说

  • 「图编排必须在每条边上重复写」——它不强制汇合，不是不允许汇合。措辞用「容易散落」「不强制」。
  • 「漏斗」这类自造词——说「同一个入口」。

5错误处理

针对模型输出的格式错误、越权工具、不合规则动作，由校验层生成带合法范围的错误提示回灌对话重试；重试超限按错误类型分别兜底：网络错误退避重试，账户错误复核后中止，动作错误由环境代选最保守合法项并标记，单局标记超限整局作废，保证记录中不混入系统代打的决策。

它在说什么

出错分四种情况，各有各的处理：

  • 网不通、网关抽风：等一会儿再试，最多两次。网关说「没钱了 / 密钥错了」，隔两秒再问一次确认，确认了整局停掉，不硬跑。每次调用有硬截止时间，超过当超时，一局不会卡死在一个请求上。
  • 模型回的东西不能用：格式坏了、调了不存在的工具、翻来覆去调同一个。把原因告诉它重来，最多三次。还不行就让环境代它做一个最保守的动作，并在记录里标记：这一步不是模型做的。
  • 模型做的动作不合规则：比如投了死人。把「为什么不行」告诉它重来，三次还不行同样兜底加标记。
  • 整局失败太多：一局里兜底超过 10 次，这局作废。再跑下去记录里一半是系统代打的，数据是假的。

一句话：能重试的重试，重试不了的兜底并标记，标记太多整局作废。每一层的兜底都被计数，「harness 替模型走了多少回合」本身就是上报的指标。

追问：真的出过吗，举例

18 局记录里每种都数得出来：格式坏了 161 次，不合规则 29 次，发言与投票不一致被拦 161 次，死循环 15 次，步数用完再问一次答对 314 次，环境代打 13 次。记录里标 forced 的回合共 24 个，占 2,827 回合的 0.78%。

追问：错误提示怎么生成的

从那个动作清单对象里生成，所以它自带正确答案。check 是一串按顺序的判断，第一个不通过的返回一句话，格式固定：哪个工具的哪个参数、给的是什么、应该是什么。合法范围那段（[2, 4, 9, 10]）不是手写的，是 Param.choices 直接打印出来的，而 choices 就是渲染进 schema 的那个列表。报错里的清单和模型一开始看到的清单永远一致。

几个取舍：一次只报一个错，模型面对一条明确指令比五条更容易改对；把错误值原样放进去，模型能对上自己刚才写了什么；前缀 [guard]，让模型知道这是系统在纠正它，不是游戏对话；不解释规则只给范围，规则解释 rules_text 里已经有，报错时重复会让模型去争辩，给范围它直接选。

追问：回灌是怎么回的

模型没有记忆，它只知道对话历史里有的东西。所以每次它调完工具，下次问它之前把两条写进历史：一条 assistant 角色，内容是它自己刚才那次调用；一条 tool 角色，内容是系统的回应，带上调用的 id 配对。这是 function-calling 协议规定的格式，缺一条 API 报错。不支持工具调用的模型走 JSON 兜底路径，同样的两条内容渲染成一段 assistant 文字加一条 user 文字。

别人怎么做

常见就两招：重试，和把错误当消息塞回给模型。LangGraph 节点可以配 RetryPolicy，工具报错以 ToolMessage 回给模型，这两点和这里一样。通常没有的三样：兜底，重试用完要么抛异常整个流程挂掉，要么自己在图里画失败分支，没有「环境给一个最保守合法动作」的概念，因为通用框架没有 action_space、不知道什么算合法；标记，就算自己写了兜底，一般不在记录里标「这一步是系统代打」，跑完分不清哪些是模型决定的；整局作废，LangGraph 有 recursion_limit 防死循环，没有「失败太多这次运行不可信」的判断。差别不在重试，在失败之后产出的数据还能不能信，这是评测场景特有的要求。

可以讲一次事故：网关连续返回 90 个 403，harness 用兜底动作填了 90 个回合，五局跑完存成了结果。那批数据全废。之后才加了终结性拒绝的分类、复核一次、整局作废。

不要说

  • 「保证系统可用性」——任何错误处理都能这么收尾，说了等于没说。
  • 「回调接口」——不是回调，是把错误原因追加进对话再调一次模型。
  • 「杜绝非法动作」——模型仍会给非法动作，只是会被拒绝并重试，最多兜底。

6幂等

以「对局 : 序号 : 座位 : 任务」为幂等键，重复到达的同一动作直接返回首次结果、不再触碰环境；真人提交按序号区分重复、过期与非法并各自返回状态而非报错，重试、双击、消息重投递都不会推进世界状态。

先看整体架构

看图顺序。先看中间上面那个循环框：一局就是一条线程跑这四行，环境、账本、玩家全在这条线程里，没有并发。再看下面两个玩家框：循环不管玩家是谁，只调 act；LLM 那个进去就出来，真人那个进去卡住等队列。最后看左边：HTTP 每个请求一条线程，观战只读，真人的 POST 走 submit 往队列里放东西，对局线程的 act 就醒了。

Pending 在哪。回合的抽象从头到尾只有 Turn。pending 是 HumanPlayer 框里的一个字段：act 卡住之前，把「我在等哪一步、清单是什么」放到上面，另一条线程的 submit 才知道拿什么去检查。图里那条 inbox.put 虚线是整张图唯一一处跨线程写入，也是唯一需要 pending 的地方。LLMPlayer 没有第二条线程，所以没有它。

它在说什么

同一个动作送来两次，世界只走一步。会送两次的三种情况：网络超时客户端重发了 POST；真人双击了「投票」；消息队列没收到确认又投递一遍。服务端收到的请求一模一样，分不出新旧。

每个回合有编号 seq，每走一步加一。动作到达时拼键 对局:seq:座位:任务，查处理过没有：处理过，把上次的结果原样返回，不碰环境；没处理过才真的 step，然后记下来。第二次「6 号在第 37 步投票」到达时，回复和第一次一样，世界停在第 38 步，不会变成 39。

真人座位多一层：提交带 seq，服务端对一下。已结算返回「重复，当时投的是 X」；比当前小返回「过期，现在是第 N 步」；不是你的回合返回「不是你」；动作不合法返回理由。都是正常返回不报错，前端按状态提示。

完整调用栈见「幂等」tab：双击的两次到达各走哪条路，逐步展开。

追问：为什么不只用 seq

座位:任务 是校验和。seq 对上但座位不对，说明客户端和服务端的认知已经分叉，应该报「过期」而不是当重复吞掉。和日志里 actor/task 是冗余校验和是同一个思路。

7记忆与上下文

每回合从视图重拼提示词、不携带历史对话，历史发言由查询工具按需读取，上下文主体不随轮数累积；每个智能体维护私有 belief 表（怀疑度、猜测角色、依据发言 id）跨回合携带，每步快照前后差异入 trace。

它在说什么

每回合模型拿到的 messages 是从零拼的：system 段从视图渲染（规则、你是谁、同伴、输出格式），situation 段从 view.public 渲染（本轮活人死人、历次投票结果、本轮全部发言、belief 摘要、这回合要做什么），回合内 ReAct 循环追加这回合的工具调用和结果，最多 8 步。上一回合模型看过什么、想过什么，这回合不带。

所以「环境记忆」是环境替它记的，每次从视图重新读出来，不是模型自己的对话历史。之前轮次的发言要看就调 query_history(player, round)。之前回合它自己的推理不在，只有它写进 belief 的那部分留下来。

追问：每个 agent 的记忆怎么操控的

每个 agent 一个 BeliefState，一张表，对每个其他座位一条：suspicion（0 到 1）、guessed_role、reason（一句话）、evidence_refs（依据的发言 id 如 r2p5）、updated_at_round。开局每人 0.5。按读 / 写 / 更新 / 淘汰 / 注入五个动作：

  • 写：只有 agent 自己，通过 update_belief 工具。harness 不替它写，环境碰不到。不能写自己，suspicion 限 [0,1]，reason 限 400 字。
  • 读：也只有自己。read_belief 读一条；每回合提示词里自动渲染「your recorded beliefs」一段，列所有活人的怀疑度和理由。
  • 注入：塞的是表的摘要，每人一行，理由截 90 字。记忆占的上下文固定，12 人局最多 11 行，和打了几轮无关。
  • 更新：覆盖不追加。同一人再 update_belief 直接改那条，旧理由丢掉。
  • 淘汰：不淘汰。表大小上限是座位数，死人的条目留着但不渲染。
  • 持久化：每回合开始和结束各拍一次快照进 trace，diff 算出这回合改了谁；续跑时 restore 从最后一份恢复。
  • 隔离：ToolContext(view, belief, task)，belief 是自己那份对象，读写不经过环境。

一句话：记忆是一张有界的结构化表，agent 自己读写，harness 只负责渲染进提示词和拍快照。

追问：模型能看到自己之前的决定吗

能看到三层，缺第四层。我做了什么：能，私有层 my_actions，环境记的。我说了什么：能，公开层发言或 query_history。我当时的判断：部分，belief 里它主动写了才有，且是覆盖后的当前版本。我当时为什么这么做：不能，上一回合的 thought 和 ReAct 过程，没进 belief 就丢了。动作的结果由环境记忆，动作的原因由 agent 自己决定记不记。

追问：为什么不做成连续的对话历史

能做，LLMPlayer 存一个 self.messages 不清空就行。要付的：

  • 和世界分叉。历史里存的是模型当时看到的文本，包括它对局面的转述，可能是错的（守卫那个例子，它记成昨晚守的是 4 号）。带历史后这个错误一直在上下文里，和视图里的真实记录并存。现在每回合重拼，错误记忆只活一回合。
  • 长度和压缩。到第 4 轮一个座位几万 token。截断丢的是开局判断，摘要由谁做、什么时候做、摘掉什么，全是新的决策点。
  • 重放要多存对话状态，且历史里有 tool_call_id 这种厂商私有字段，换模型续跑对不上。
  • 真人没有对话历史，对等性弱一点。

折中：每回合结束让模型写一段「给下回合的自己的话」，存进 belief 旁边一个 note 字段，下回合注入。是便条不是录音，长度固定、可重放、真人也能有。它补的正是第四层「我为什么这么做」。目前没做。

追问：上下文真的不随轮数增长吗

说「不增长」过了。会长的：死亡列表每死一人多一行，历次投票结果每轮一行，狼的私聊记录和分工变更历史。不长的：本轮发言只放当前轮，belief 摘要上限是活人数，回合内步数上限 8。所以是线性且缓慢的增长，一轮多几行，主体（规则、本轮发言、工具 schema）是常量。简历上写「主体不随轮数累积」。

追问：「执行上下文不含环境对象」什么意思

每个查询工具的签名是 def _query_votes(ctx: ToolContext, args)，ctx 只有三个字段：view（observe 给的裁剪后视图）、belief（自己的笔记）、task。没有 env。工具想查票型只能从 ctx.view["public"]["votes"] 读，想查底牌没处读。对比把 env 传进工具的写法，工具能读 env._roles、能改 env._alive，成了绕过 observe 的第二条通道和第二个写入口。所以工具和模型看到的是同一份视图，工具只能翻视图，翻不出视图里没有的东西。

8模型接入与观测

模型接入：厂商方言怎么处理

六家都说自己「OpenAI 兼容」，但每家偏一点：DeepSeek 开着思考不接受 tool_choice=required；Kimi 只认一个 temperature，思考开关不同这个值不同（0.6 或 1）；GLM-5.3 永远在思考，传 disabled 直接 400；Gemini 的 schema 不接受整数 enum，选人回合必然 400。常见做法是客户端里 if model.startswith("kimi")，每接一家加一段分支。这里客户端只有一条路径，每个模型是表里的一行，方言写成字段：temperature、extra_body、tool_choice。加第七家是加一行，不改客户端。

两类信息分开标：base_url 是真的探过的（每家回了结构化 401），模型 id 和参数是从文档抄的可能过期，verified=True 和 measured 只有用真实 key 打通过才填。退役而不删：glm-4.7-flash 免费共享算力 16 次 15 次 429，标 retired 留在表里，菜单不显示但能看到为什么没用。

观测：页面能看什么

零依赖观战页，服务端 ThreadingHTTPServer 加 SSE，前端原生 JS。圆桌、按轮筛选的发言和票型、点座位看该 AI 这回合的决策链（查了哪些工具、每步 thought、被拦几次）、健康度、复盘讨论、测试模式全局透视。

追问：测试模式怎么实现的

一个布尔值加一个门。开局表单选「测试模式」，POST 带 xray: true，存到 Game.xray，之后不能改。服务端给页面数据的接口只有两个：seat_state(seat)（实时状态，打开牌桌时拉一次，之后每收到一个 SSE 事件拉一次）和 full_log(seat)（完整记录，切到「全部记录」tab 时拉）。两个函数开头都调 _may_see_all(seat)：

def _may_see_all(self, seat):
    if self.xray or self.state in ("over", "aborted", "crashed") or self._reviewing():
        return True                          # 测试模式 / 局结束 / 复盘中
    if seat:
        return seat not in self.env._alive   # 已出局的座位可以看全场
    return False

四扇门任一开着放全量：底牌 revealed、每座位决策链 traces、journal 里带 thought 的原始动作。都关着只给公开任务的记录，动作先过 _public_action 剥掉 thought，traces 给空。xray 不改 observe，模型座位拿到的视图和正常模式一样，对局本身没区别，测试模式的局可以进统计。前端只做显示，拿到 revealed 就标角色，没拿到就没那些按钮，判断全在服务端。前端开关等于没开关，改一下 localStorage 就绕过了。

「同一个门」的实现就是：判断写成一个方法，两个接口各调一次拿布尔值当开关，不把那串条件在两处各抄一遍。论文里那次泄露就是 full_log 当时没过这个门。

9复盘

对局结束后开放复盘阶段：结果冻结后全部信息解密交给各智能体轮流讨论，走同一套动作与记录机制，作为跨局经验沉淀的入口。

胜负判定之后环境不直接结束，先进 review 阶段。所有座位，活的死的，轮流发言或过，一整轮全员都过或到上限轮数（默认 2）才真正结束。每轮是每座位一次调用，12 人局一轮 12 次，上限轮数既是规则也是预算。

追问：agent 不是该调 observe 看世界吗，这次不是了？

还是 observe，没有第二条路，只是这个阶段给得更多。observe 末尾三行：if self._phase == "review": v["review"] = self._review_handout()。_review_handout() 是私有方法，只是 observe 内部拼视图的一个零件。对智能体流程没变，视图里多了个 review 键。

追问：那个键里是什么

这局的全部真相：winner、rounds_played、roles（每座位真实角色）、teams、survivors、deaths（第几轮、谁、怎么死）、night_actions（每晚每个角色刀谁守谁救没救毒谁）、seer_checks、wasted_knives（被挡掉的刀）、pack_chat（狼私聊全文）、pack_plans（分工及变更）。平时这些散在 private 层按角色给，复盘时全摊开，所有座位拿到的这份完全一样。

这是隔离保证里唯一有意的洞，但它是时间上的洞：只在 _phase == "review" 时才有，而这个阶段只在 _finish 冻结胜负之后才出现。早一回合读不到，读到了也改不了结果。隔离测试照跑，只是在 review 阶段把断言换成「全员看到同一份真相」。

以后要做跨局记忆，入口就是这里：复盘发言总结成结构化教训入库，新局 observe 的 private 多一个 lessons 键注入，走同一道门；评估走同种子配对。

10数据与边界

被问「效果怎么样」时能报的数字，和不能报的：

  • 18 局 12 人局、2,827 回合，兜底率 0.78%。兜底率是 harness 健康度——harness 替模型走完的回合占比——不是模型可靠性。这个定性别说错。
  • 同种子配对 A/B，9 对，评估「狼队每晚重新协商」：未检测到显著差异（相同 4，双向翻转 2 比 3）。如实说样本不足，并说出从中发现的自身指标缺陷：把「约定目标已出局」误计为违约，对照组 96 次投票全为无效样本。这条比编一个结论有说服力。
  • 没做的，主动说：沙箱（工具全是纯查询，没有副作用要隔离）、长程记忆（单局上下文可控）、分布式（一局一线程）、规模（最大 15 座位）。结论限于回合制、进程内、十几个参与者、工具无副作用的对抗环境。
  • 自研的固有成本：没有生态，无人认识它。团队已在用编排框架且场景是协作型时，沿用它更好。

11简历定稿

Werewolf Arena——多模型狼人杀对局引擎　独立项目

技术栈：Python 标准库（零第三方依赖）、OpenAI-compatible API、DeepSeek / Kimi / GLM / Claude、SSE、原生 JS

  • 项目背景：针对狼人杀这类多智能体对抗场景中狼、神职、村民各自认知不同、而通用编排框架把整局状态交给每个节点、容易泄漏的问题，实现一个多模型狼人杀对局引擎：由引擎持有底牌与夜间记录、为每个座位裁剪各自可见的视图、按局面生成合法动作、统一写入并可重放，DeepSeek / Kimi / GLM / Claude 与真人可混坐同一局。
  • 上下文隔离：针对对抗任务中不同 agent 可视环境不同的问题，设计三层视图结构，输出一份针对不同角色裁剪后的环境，可见性只在生成视图时判断一次、提示词与页面渲染不含任何角色逻辑，真人与模型拿到同一份视图、真人侧零过滤代码；隔离测试对整局每回合每座位断言无身份泄露。
  • 合法动作集：每回合由当前环境状态推出该角色的合法动作集，同一份既渲染为工具 schema、又作为执行前校验依据，校验只做「是否在集合内」的通用判断、不重写任何规则；规则只在一处定义，避免提示词与校验各自维护一份规则而产生不一致。
  • 唯一写入口与重放：统一的执行函数作为改变环境状态的唯一入口，环境完全由初始状态和动作日志决定，中断后同种子重放日志即可恢复到断点、不调用模型，日志即追溯记录；同一局 81 回合实测日志 8 KB 对快照 526 KB。
  • 状态索引的控制流：各条路径只负责写入状态，调度只依据当前状态决定下一步、不关心经哪条路径到达，后果规则从「每条路径 × 每条规则」各判断一次降为「路径数 + 规则数」，新增规则只改一处；并以不可变集合加静态检查保证所有状态变更都经过同一个函数。
  • 多智能体编排：12 个独立 agent 由不同模型驱动，无中心调度节点，环境按状态返回下一个行动者；狼队夜间私有频道多轮协商与分工，白天全员轮流发言、竞选、投票；真人可替换任一 agent 且环境无法区分。
